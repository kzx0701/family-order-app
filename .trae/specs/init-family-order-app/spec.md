# 家庭点餐小程序 Spec

## Why
为家庭成员（老婆下单、丈夫做饭）打造一个无支付的内部点餐小程序。区别于市面商家点餐系统，本系统无任何支付逻辑、流程、接口，专注于"家庭成员间点单沟通"场景：老婆通过小程序下单，丈夫（管理员兼厨师）接收订单、制作并标记完成。整体风格趣味可爱、动效丝滑，区别于商业点餐系统的严肃感，少文字多图片素材。

## What Changes
- 新建微信小程序项目（基于 uniapp + uniCloud 编译为微信小程序）
- 微信登录 + 单家庭共享用户体系，首次进入选择角色（下单人/管理员），后续记住
- 底部 tab 差异化：下单人 3 tab（首页/点单/记录），管理员 4 tab（首页/点单/记录/管理）
- 首页：咖啡/美食双入口卡片 + "今日订单"区域（角色差异化展示）
- 点单页：咖啡（棕色主题）与美食（绿色主题）共用同一页面，左侧分类导航 + 右侧菜品列表，支持列表直接加购与详情页加购双入口
- 菜品详情页：大图 + 描述 + 数量选择 + 加入点单（无规格自定义）
- 购物车：底部购物车条 + 浮层展开改数量/删除
- 提交详情页：产品只读列表 + 预约时间（尽快/指定二选一）+ 备注，点单人默认当前用户
- 下单成功结果页：成功动效 + 订单详情卡片 + 返回首页/查看记录
- 订单三状态流转：待制作 → 制作中 → 已完成，仅待制作状态可取消
- 管理员管理 tab：菜单 CRUD（含菜品图上传、分类管理、上下架）+ 订单状态操作
- 记录页：按日期分组列表展示，无筛选
- 双向微信订阅消息推送（下单→管理员，完成→下单人）
- 完全移除价格字段，无任何支付逻辑
- 趣味可爱视觉风格，丝滑动效，多用图片少用文字

## Impact
- Affected specs: 全新项目，无既有 spec 受影响
- Affected code: 全新项目结构，主要包含：
  - uniapp 前端（pages / components / static / store）
  - uniCloud 云函数 + 云数据库（users / dishes / categories / orders 集合）+ 云存储（菜品图片）
  - 微信公众平台订阅消息模板配置

## 技术架构

### 前端框架
- **uniapp + Vue 3 + Composition API**：跨平台框架，编译为微信小程序，采用 Vue 3 现代语法
- **状态管理：Pinia**：管理用户信息、角色、购物车等跨页面共享状态
- **样式方案：SCSS + CSS 变量**：基于 colors_and_type.css 的设计 token，建立全局 SCSS 变量统一管理双主题（咖啡棕/美食绿）

### UI 组件方案
- **纯自定义 UI 组件**：不使用第三方 UI 库（uView/uni-ui 等），全部组件自行实现
- **理由**：项目功能简单（无复杂表格/树形/数据看板），但视觉风格要求极高（趣味可爱、丝滑动效、少文字多图）。第三方 UI 库风格偏商业，强行覆盖样式会冲突
- **基础组件**：输入框、日期时间选择器、按钮、卡片等参考 uni-ui 实现思路自写，确保风格统一
- **图标方案**：SVG 图标（lucide 风格），可缩放可着色

### 动画方案
- **CSS transitions/animations**（主用）：页面切换、状态过渡、按钮反馈、加购飞入动效，性能好
- **Lottie（lottie-miniprogram）**（辅助）：下单成功庆祝动画、首页装饰插画等复杂动画
- **加购飞入动效**：CSS transform 路径动画实现菜品图飞入购物车

### 图片资源
- **菜品图**：管理员通过 uniCloud 云存储上传（uniCloud.uploadFile）
- **UI 装饰图/插画**：项目内置 static 资源（SVG 或 Lottie）

### 后端架构
- **uniCloud 云数据库**：4 个集合（users / dishes / categories / orders）
- **DB Schema**：用于 dishes / categories 的标准 CRUD，自动生成接口与数据校验，减少代码量
- **自定义云函数**：处理业务逻辑（user-login 登录鉴权、orders-crud 订单状态流转、subscribe-message 订阅消息推送、home-data 首页聚合数据、menu-list 菜单查询）
- **云存储**：菜品图片存储与 CDN 分发

### 微信能力
- **登录**：uni.login + uniCloud uniID 用户体系，在 users 集合扩展 role 字段实现角色系统
- **订阅消息**：wx.requestSubscribeMessage（一次性订阅模式）
  - **限制说明**：微信订阅消息为"一次性授权 = 一次发送"，每次老婆下单需重新授权
  - **优化方案**：提交前一次性请求多个模板授权（同时授权"通知管理员"和"接收完成通知"两个模板）
  - **模板配置**：在微信公众平台配置"下单通知"和"完成通知"两个模板

## ADDED Requirements

### Requirement: 微信登录与角色选择
系统 SHALL 提供微信一键登录，登录后首次进入需选择角色（下单人/管理员），选择后持久化记住，后续自动识别角色。

#### Scenario: 首次登录选择角色
- **WHEN** 用户首次微信登录完成
- **THEN** 弹出角色选择页，提供"下单人"和"管理员"两个选项
- **AND** 用户选择后，角色信息存储到 users 集合，后续登录自动识别

#### Scenario: 角色差异化 tab
- **WHEN** 下单人进入小程序
- **THEN** 底部显示 3 个 tab：首页、点单、记录
- **WHEN** 管理员进入小程序
- **THEN** 底部显示 4 个 tab：首页、点单、记录、管理

### Requirement: 单家庭共享数据
系统 SHALL 所有用户共享同一家庭空间，任何用户可看到所有家庭成员的点单记录。

#### Scenario: 共享订单可见
- **WHEN** 任一家庭成员提交订单
- **THEN** 所有家庭成员在记录页均可看到该订单
- **AND** 订单详情中显示点单人身份

### Requirement: 首页双入口与今日订单
系统 SHALL 在首页提供咖啡和美食两个点单入口，并根据当前用户角色展示今日订单区域。

#### Scenario: 下单人首页
- **WHEN** 下单人进入首页
- **THEN** 显示咖啡/美食两个入口卡片
- **AND** 显示"今日我的点单"列表，仅展示当前用户今日提交的订单

#### Scenario: 管理员首页
- **WHEN** 管理员进入首页
- **THEN** 显示咖啡/美食两个入口卡片
- **AND** 显示"今日待制作订单"列表，展示所有待制作和制作中状态的订单
- **AND** 支持直接操作订单状态（开始制作/完成）

### Requirement: 咖啡与美食点单页
系统 SHALL 提供统一的点单页面，咖啡和美食共用，仅数据与配色主题不同（咖啡棕色 / 美食绿色）。

#### Scenario: 进入点单页
- **WHEN** 用户点击咖啡入口
- **THEN** 进入点单页，主题色为咖啡棕系（主色 #6F4E37，辅色 #F5E6D3），加载咖啡分类与咖啡菜品
- **WHEN** 用户点击美食入口
- **THEN** 进入点单页，主题色为美食绿系（主色 #16A34A，辅色 #DCFCE7），加载美食分类与美食菜品

#### Scenario: 分类切换
- **WHEN** 用户点击左侧分类导航
- **THEN** 右侧菜品列表滚动到对应分类位置
- **AND** 当前分类高亮显示

#### Scenario: 列表直接加购
- **WHEN** 用户点击菜品列表项的"+"按钮
- **THEN** 该菜品加入购物车，购物车数量+1
- **AND** 底部购物车条更新件数，伴随趣味动效

### Requirement: 菜品详情页
系统 SHALL 提供菜品详情页，展示大图、名称、描述、数量选择和加入点单按钮。无规格自定义。

#### Scenario: 进入详情页
- **WHEN** 用户点击菜品列表项的图片或名称
- **THEN** 进入菜品详情页，展示大图（管理员上传的图片）、名称、描述、数量选择器、加入点单按钮

#### Scenario: 加入点单
- **WHEN** 用户在详情页选择数量并点击"加入点单"
- **THEN** 对应数量的菜品加入购物车
- **AND** 返回点单页，购物车条更新

### Requirement: 购物车浮层
系统 SHALL 在点单页底部显示购物车条，点击展开浮层可修改数量和删除。

#### Scenario: 购物车条展示
- **WHEN** 购物车有商品
- **THEN** 底部购物车条显示总件数和"去下单"按钮
- **WHEN** 购物车为空
- **THEN** "去下单"按钮置灰

#### Scenario: 展开浮层
- **WHEN** 用户点击购物车条
- **THEN** 丝滑展开浮层显示所有已选菜品列表
- **AND** 每条可"+/-"调整数量或删除

### Requirement: 提交详情页
系统 SHALL 提供提交详情页，展示只读产品列表、预约时间选择和备注输入。

#### Scenario: 进入提交详情页
- **WHEN** 用户点击"去下单"
- **THEN** 进入提交详情页，展示已选菜品只读列表、预约时间选择、备注输入框
- **AND** 点单人默认为当前登录用户

#### Scenario: 预约时间选择
- **WHEN** 用户选择预约时间
- **THEN** 提供"尽快"和"指定时间"两种模式二选一
- **AND** 选择"指定时间"时展开日期+时间选择器

#### Scenario: 提交订单
- **WHEN** 用户点击提交按钮
- **THEN** 创建订单（状态为待制作）
- **AND** 发送订阅消息通知管理员
- **AND** 跳转到下单成功结果页

### Requirement: 下单成功结果页
系统 SHALL 在订单提交成功后展示成功页，包含成功提示和订单详情。

#### Scenario: 成功展示
- **WHEN** 订单提交成功
- **THEN** 展示成功动效与趣味提示文案
- **AND** 展示本次订单详情（菜品列表、预约时间、备注、点单人、提交时间）
- **AND** 提供"返回首页"和"查看记录"按钮

### Requirement: 订单三状态流转
系统 SHALL 订单状态包含待制作、制作中、已完成三个状态，仅管理员可推进状态。

#### Scenario: 状态流转
- **WHEN** 订单创建后状态为"待制作"
- **AND** 管理员点击"开始制作"
- **THEN** 状态变为"制作中"
- **AND** 管理员点击"完成"
- **THEN** 状态变为"已完成"，发送订阅消息通知下单人

#### Scenario: 订单取消
- **WHEN** 订单处于"待制作"状态
- **THEN** 下单人可取消自己的订单，管理员可取消任何订单
- **AND** 订单状态变为"已取消"，不再进入流转
- **WHEN** 订单已进入"制作中"或"已完成"
- **THEN** 不可取消

### Requirement: 记录页
系统 SHALL 提供记录页，按日期分组展示所有订单，无筛选。

#### Scenario: 记录展示
- **WHEN** 用户进入记录页
- **THEN** 按日期倒序分组展示所有订单
- **AND** 每条订单显示：菜品摘要、状态标签、点单人、提交时间
- **AND** 状态标签颜色区分（待制作/制作中/已完成/已取消）

#### Scenario: 管理员操作订单
- **WHEN** 管理员点击订单卡片
- **THEN** 可操作订单状态变更（开始制作/完成/取消）

### Requirement: 管理员管理 tab
系统 SHALL 为管理员提供独立的管理 tab，包含菜单管理和订单管理。

#### Scenario: 菜单管理
- **WHEN** 管理员进入管理 tab
- **THEN** 可查看所有菜品列表，按咖啡/美食分类筛选
- **AND** 可新增菜品（名称、图片上传、描述、所属分类、是否上架）
- **AND** 可编辑/删除菜品

#### Scenario: 分类管理
- **WHEN** 管理员进入分类管理
- **THEN** 可新增/编辑/删除/排序分类（咖啡和美食各自独立）

#### Scenario: 菜品上下架
- **WHEN** 管理员切换菜品上架状态
- **THEN** 下架菜品不在点单页展示

#### Scenario: 订单管理
- **WHEN** 管理员查看订单管理
- **THEN** 可查看所有订单并操作状态变更

### Requirement: 菜品分类
系统 SHALL 咖啡和美食各自有独立的子分类，由管理员维护。

#### Scenario: 分类展示
- **WHEN** 进入点单页
- **THEN** 左侧显示当前类型（咖啡/美食）的所有分类导航
- **AND** 包含"推荐"分类置顶

### Requirement: 双向微信订阅消息
系统 SHALL 通过微信订阅消息实现双向通知。

#### Scenario: 下单通知管理员
- **WHEN** 下单人提交订单
- **THEN** 向管理员发送订阅消息，包含订单摘要和点单人

#### Scenario: 完成通知下单人
- **WHEN** 管理员将订单标记为已完成
- **THEN** 向下单人发送订阅消息，包含订单摘要

#### Scenario: 订阅授权
- **WHEN** 下单人首次提交订单前
- **THEN** 请求订阅消息授权

### Requirement: 无支付逻辑
系统 SHALL 完全不包含任何价格字段、支付流程、支付接口。菜品数据模型中无 price 字段，所有界面不展示价格。

#### Scenario: 无价格展示
- **WHEN** 任何页面展示菜品或订单
- **THEN** 不显示价格信息
- **AND** 菜品数据模型不包含 price 字段

### Requirement: 趣味可爱视觉风格
系统 SHALL 采用趣味可爱、美观的视觉风格，区别于商业点餐系统的严肃感，配合丝滑动效，少文字多图片素材。

#### Scenario: 双主题配色
- **WHEN** 进入咖啡点单页
- **THEN** 主题色为咖啡棕系（#6F4E37 主色，#F5E6D3 辅色）
- **WHEN** 进入美食点单页
- **THEN** 主题色为美食绿系（#16A34A 主色，#DCFCE7 辅色）

#### Scenario: 丝滑动效
- **WHEN** 页面切换、加入购物车、状态变更等交互发生
- **THEN** 使用丝滑过渡动效，无生硬样式切换

#### Scenario: 趣味加购动效
- **WHEN** 用户点击"+"加购
- **THEN** 触发趣味动效（如菜品图飞入购物车）

### Requirement: 技术架构规范
系统 SHALL 采用以下技术栈实现，所有技术选型需符合规范。

#### Scenario: 前端框架
- **WHEN** 项目初始化
- **THEN** 使用 uniapp + Vue 3 + Composition API
- **AND** 状态管理使用 Pinia
- **AND** 样式使用 SCSS + CSS 变量统一管理设计 token

#### Scenario: UI 组件方案
- **WHEN** 实现界面组件
- **THEN** 全部自定义实现，不使用第三方 UI 库（uView/uni-ui 等）
- **AND** 基础组件（输入框、选择器、按钮等）参考 uni-ui 实现思路自写
- **AND** 图标使用 SVG（lucide 风格）

#### Scenario: 动画方案
- **WHEN** 实现页面切换、状态过渡、按钮反馈等基础动效
- **THEN** 使用 CSS transitions/animations
- **WHEN** 实现下单成功庆祝动画、首页装饰插画等复杂动画
- **THEN** 使用 Lottie（lottie-miniprogram）

#### Scenario: 后端架构
- **WHEN** 实现 dishes / categories 的标准 CRUD
- **THEN** 使用 uniCloud DB Schema 自动生成接口与数据校验
- **WHEN** 实现登录鉴权、订单状态流转、订阅消息推送等业务逻辑
- **THEN** 使用自定义云函数处理
- **AND** 菜品图片通过 uniCloud 云存储上传

#### Scenario: 微信订阅消息
- **WHEN** 老婆提交订单前
- **THEN** 一次性请求多个模板授权（通知管理员 + 接收完成通知）
- **AND** 使用 wx.requestSubscribeMessage（一次性订阅模式）
